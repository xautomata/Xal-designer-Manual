# Updating XAL

When the scenario changes after the XAL has already been generated, use **Update XAL** to bring the changes into the existing file without regenerating it from scratch. The edits you made by hand on the XAL are kept.

---

## When Update XAL appears

The toolbar of the scenario tab shows only the actions that apply. The first icon is the status badge: move the mouse over it to read the state.

| Situation | Badge | Toolbar |
|---|---|---|
| No XAL yet, or an XAL uploaded and never generated by Arianna | Grey circle | **Generate XAL** (green): see [Generating XAL](generating_xal.md) |
| Scenario and XAL aligned | Green check, *Up to date* | No generate button |
| The scenario changed since the last generation | Blue arrow | **Update XAL** (orange) |
| The XAL was edited by hand, the scenario did not change | Orange pencil | **Sync Scenario** only: see [Syncing the Scenario](syncing_scenario.md) |
| Both changed | Yellow warning | **Update XAL** (orange) and **Sync Scenario**, in a yellow frame with a warning icon |

When both files changed, each action overwrites the changes of the other file: **Update XAL** rewrites the XAL from the scenario, **Sync Scenario** rewrites the scenario from the XAL. Update XAL starts at once, with no confirmation, and keeps the edits made by hand that it can carry over (see below).

---

## What is different from Generate XAL

When generating for the first time, Arianna builds the automaton graph from scratch. When updating, it receives the **existing graph** alongside the new scenario and produces only the changes required — preserving unchanged states, transitions, and node identifiers.

This surgical approach avoids unnecessary restructuring of an automaton that may already be partially or fully correct.

The context Arianna receives depends on what is available in the current session:

| Available | Context passed to Arianna |
|---|---|
| `.dot` file from a previous generation | New scenario + existing `.dot` (preferred — most structural context) |
| No `.dot`, but XAL exists | New scenario + existing XAL (used as structural reference) |

The `.dot` file is retained internally by the session after each generation. It is not shown in the repository explorer, but it is used automatically by **Update XAL** when available.

The rest works as in a generation: the same [steps and progress card](generating_xal.md#the-steps), the file locked until the end, **Cancel** to stop.

---

## Edits made by hand

If you edited the XAL in the Designer after the last generation, **Update XAL** carries your edits into the new XAL. These are typically the values that Arianna leaves for you to complete, for example:

- the inputs of the automata that an automaton creates;
- the systems that a function calls (name, class and path), and its inputs and outputs;
- the text of the queries;
- the types and values of the Global State variables.

Functions and Global State variables that you added or removed by hand are carried over too.

Some edits are not carried over:

- states, transitions and automata added or removed by hand: the structure of the automaton comes from the scenario, so describe them in the scenario;
- edits on an element that the update removed;
- edits on a value that the update changed too;
- edits that would point to a function or a Global State variable that no longer exists;
- all the edits, if together they would make the XAL invalid.

After the update, the chat lists the edits carried over and the ones that were not, each with the reason. Redo in the Designer the ones you still need.

---

## After updating

The XAL file is overwritten with the new version and reloaded in the graph. The status badge shows *Up to date* again. The chat shows the same warnings as after a [generation](generating_xal.md#after-the-generation).

If the update introduces validation errors, the same [automatic retry and download fallback](generating_xal.md#if-all-attempts-fail) as a fresh generation applies.
